# Listing a project

Get a project into the lists that fit it, through each list's own allowed route.

**Each list's own files decide the route; the owner's explicit yes, per target, decides whether anything public is created. A submission that breaks either one gets closed and can get the project banned from the list.**

Track every target in one table, `listing.md` in the scratch area, and update its row after each step. Columns, in order:

| Directory | Route | Eligibility | Status | Link or next action |
|---|---|---|---|---|

Status is one of: `skip: <reason>`, `already listed`, `crawler: <condition>`, `ready`, `submitted`, `needs human`, `waiting until <YYYY-MM-DD>`, `waiting: <unmet condition>`.

## 1. Find candidates and check activity

Search for lists that fit the project's ecosystem and kind: GitHub search for `awesome <ecosystem>`, topic pages, the ecosystem's official directory or marketplace. For each GitHub candidate run:

```bash
gh repo view <owner>/<repo> --json nameWithOwner,isArchived,pushedAt
gh search prs --repo <owner>/<repo> --merged --sort updated --limit 1 --json updatedAt  # merged PRs only; updatedAt ≥ merge date
```

- `nameWithOwner` differs from what you typed → the repo moved. Use the new owner from here on; the row names where a PR really lands.
- Archived, or the newest merge is older than 6 months (tunable) or absent → `skip: inactive since <date>`. Prepare nothing for it. Before skipping for no merges, read the README: a list generated by a crawl has no merges and is judged by `pushedAt` instead.
- The list covers a different kind of project → `skip: no fit`.

Done when `listing.md` has one row per candidate, and each row is skipped with a reason or names its current owner/repo.

## 2. Read each list's rules exactly

Read `CONTRIBUTING.md`, the README's contributing section, `.github/ISSUE_TEMPLATE/*` and `.github/PULL_REQUEST_TEMPLATE*` of every remaining candidate, today. Rules you remember are stale; a threshold not quoted from today's files is a guess. Record in the row:

- **Route**: PR, issue form, web form, or none. A list that says it is generated from topics, stars or a crawl is `crawler: <condition>`: it needs no submission, only the condition (step 6).
- **Who may submit**: "web form only", "no CLI or bot submissions", "the author opens the issue" mean an agent never submits there. The row becomes `needs human` with the exact form URL.
- **Eligibility**: minimum repo age, stars, licence, release, docs. Check it with `gh repo view <owner>/<project> --json createdAt,stargazerCount`. An unmet age rule → `waiting until <date>`; an unmet rule with no date (stars, licence, release) → `waiting: <condition>`.
- **Format and ordering**: the entry line format, the section, and the sort order.

Done when every non-skipped row has a route, an eligibility verdict with a date or unmet condition, and its rules quoted from the list's own files.

## 3. Check the project is not already listed

```bash
gh api repos/<owner>/<repo>/readme -H 'Accept: application/vnd.github.raw' | grep -in '<project>'
gh search prs --repo <owner>/<repo> '<project>' --limit 100 --json url,state
gh search issues --repo <owner>/<repo> '<project>' --limit 100 --json url,state
```

If the list keeps entries in other files (linked from the README, `data/`, `*.json`, `*.yml`), grep those too. A search that returns its full limit may be truncated: narrow the query. A failed read is `unchecked`, never "none"; an `unchecked` row is not `ready`. A hit on the default branch → `already listed`. An open PR or issue → `submitted` with its link. A closed, unmerged one → read why; that reason usually still applies.

Done when each row records the three results (hit, link, "none" or `unchecked`).

## 4. Prepare each entry

Write the entry in the list's exact format into `listing.md` under its row: the line, the section heading, and the position. If the section's existing order breaks the stated rule (for example it is not alphabetical), no position follows the rule; append at the end of the section and say so in the PR body, so the maintainer can place it. For a form, write the answer to each field.

Done when every `ready` or `needs human` row has its entry text, section and position.

## 5. Ask the owner, then submit through allowed routes

A fork, PR, issue or comment on a third-party repo creates public surface under the owner's name. Before the first such command, show the owner the table and the entries and ask, per target: "Submit to <list> via <route>? (yes/no)". Record each answer in the row. A general "go ahead" or "submit everywhere" names no targets and no routes; ask per target anyway.

If the harness or a permission classifier denies a fork, PR or issue, mark that target `needs human: denied by permission system` and tell the owner. Never retry it another way (another tool, command or the web UI); the denial is the owner's environment saying no, and only the owner can lift it.

Submit only to rows that are `ready` (eligibility met, a route the list allows an agent to use) and carry a recorded yes. For a PR: fork, branch, add the entry, open the PR with the list's template filled in. For an issue form that allows agents: fill every field of the form's template. Record the link.

Done when every row is `submitted` with a link, or carries another status with its reason, and every public action has a recorded yes.

## 6. Improve the project's own discoverability

Suggest repository topics that crawler lists and search read (the ecosystem and project kind, for example `claude-code`, `claude-code-plugin`) and a one-line description with those terms. Apply them only after the owner's yes: `gh repo edit <owner>/<project> --add-topic <topic>`.

Done when the topics are in the report, applied or marked declined.

## 7. Report

Give the owner the final table. Every `needs human` or `waiting` row names the URL to open and the earliest date or condition, for example `needs human: https://github.com/<owner>/<repo>/issues/new?template=submit.yml, from 2026-10-25 (repo age ≥ 14 days)`.

Done when the report shows one row per candidate and every `needs human` or `waiting` row carries a URL and a date or condition.
